# 나만의 자산관리사: 지속형 금융 에이전트 설계

2026-09-24. 제품 방향 제안이다. 현재 구현된 지속형 팀이나 실제 거래 기능을 뜻하지 않는다. 사용자의 핵심 경험은 **한 사람처럼 이어지는 ALPHA와의 대화**이고, VAULT와 WATCH는 고정된 책임을 가진 전문가로 뒤에서 일한다. [xAI의 Grok Bot 설계 설명](https://x.ai/news/designing-grok-bot)은 세션 대신 이름·역할·기억·루틴을 가진 Bot을 제품의 중심 객체로 둔다. 여기서는 그 관계 구조를 금융 의사결정에 맞게 설계한다.

## 사용자에게 보이는 팀

| 이름 | 사용자에게 보이는 직함 | 지속적인 책임 | 할 수 있는 일 | 행동 경계 |
|---|---|---|---|---|
| **ALPHA** | 나의 자산관리사 | 사용자의 목표와 조건을 이어받고 계획 전체를 설명 | 질문 정리, WATCH·VAULT 결과 합치기, 2개 이상 배분안과 유보 제시, 조건 변경 시 재계산 요청 | 거래 가능성·최적성·수익을 근거 없이 선언하지 않음; 서명·구매를 대신하지 않음 |
| **VAULT** | 유동성 매니저 | 현금성 보유액, 출금 시점, 잠금·비용 조건 관찰 | 필요한 즉시 보유액과 계획의 출금 충돌 검사 | 시장의 `cash`를 사용자의 확정 출금 가능액으로 취급하지 않음 |
| **WATCH** | 온체인 애널리스트 | TRON 상품·계약·금리·담보·원천의 변화 관찰 | JustLend·USDD 원문 시각과 변동 근거 연결, 오래된 계획 표시 | 확인되지 않은 약관과 실행 경로를 추정하지 않음 |

처음에는 ALPHA 한 명과 대화한다. 사용자가 매번 누구에게 일을 시킬지 고르지 않는다. ALPHA가 VAULT와 WATCH의 결과를 모으고, 원하면 해당 직원의 작업 기록을 펼쳐 볼 수 있다. 별도 채팅을 여는 것은 해당 역할과 오래 이어지는 대화가 필요할 때만 한다. ‘Trader’라는 직함은 실제 주문·체결 경로가 검증되기 전까지 ALPHA의 거래 권한을 암시하므로 주 역할명으로 쓰지 않는다.

## 첫 화면과 상호작용

기존 [대화 화면](../../web/index.html)의 세 열을 유지하되, 왼쪽은 **대화 목록** 대신 팀 명단으로 바꾼다. `ALPHA · 대기 중인 결정 1`, `VAULT · 출금 조건 확인 중`, `WATCH · 새 근거 2`처럼 이름·책임·실제 작업 상태를 한 줄로 보여준다. 가운데는 언제 돌아와도 같은 ALPHA와 이어지는 대화다. 상단에는 사용자가 확인한 자산 목표와 다음 점검 시점을 간결하게 둔다. 오른쪽 작업 공간에는 검색 후에만 상품·배분안·비용·출구·근거를 보여주는 카드를 연다. 상품 카드의 조밀한 정보 위계는 사용자가 지정한 Fomo 참고 화면 방향을 따르고, 대화/작업 공간의 관계는 WHOLLET 참고 화면을 따른다.

대화에는 문장뿐 아니라 네 가지 객체가 끼어든다: **진행 중인 일**, **오늘의 발견**, **계획 비교**, **승인 요청**. 예를 들어 “한 달 뒤 500 USDT가 필요해”라고 말하면 ALPHA가 조건을 확인하고, VAULT가 즉시 보유액·출금 증거를 확인하고, WATCH가 현재 상품 원천을 확인한다. 오른쪽에 두 배분안을 띄우되 필수 출금 약관이나 비용이 없으면 카드에 `확인 중`을 표시하고 구매 버튼을 열지 않는다. 사용자가 조건 하나를 고치면 옛 계획과 승인 요청은 만료시키고 새 버전을 만든다.

상태는 실제 작업 이벤트에서만 `대기`, `조회 중`, `근거 부족`, `사용자 답변 대기`, `승인 대기`, `완료`로 바뀐다. 수집기가 돌고 있다는 사실만으로 직원이 특정 사용자의 자산을 감시 중이라고 표시하지 않는다. 현재 웹 화면은 대화→조건 확인→읽기용 두 계획을 보여줄 뿐, 명단·장기 기억·개인 루틴·구매는 구현되지 않았다.

## 직원의 일이 계속 이어지는 방식

각 직원은 `owner`, `job`, `trigger`, `reads`, `output`, `escalation`, `allowed_actions`, `last_run`, `next_run` 계약을 갖는다. 루틴은 LLM을 계속 켜두는 대신 **예약 작업 또는 검증된 데이터 변화 이벤트**로 시작한다. 첫 루틴은 다음 셋이면 충분하다.

1. WATCH의 원천 변화 점검: 새 수집본의 시각·해시·값을 이전 것과 비교한다. 변화가 사용자 계획에 영향을 줄 때만 ALPHA에게 전달한다.
2. VAULT의 기한 점검: 사용자가 확인한 출금일이 가까워지거나 현재 계획이 필요 현금과 충돌하면 ALPHA에게 알린다. 출금 약관이 없으면 자료 확보 대기로 둔다.
3. ALPHA의 개인 브리핑: 최신 근거와 사용자 조건에 실제 변화가 있을 때만 “무엇이 달라졌는지, 어떤 선택이 필요한지”를 한 번에 요약한다. 단순 가격·금리 흔들림마다 메시지를 보내지 않는다.

사용자는 각 루틴을 보고 켜고 끌 수 있다. 통지에는 관측 시점과 변경 이유를 붙인다. 작업 실패는 성공이나 침묵으로 가장하지 않고 해당 루틴의 상태로 남긴다.

## 기억과 근거의 분리

‘ALPHA가 나를 기억한다’는 대화 전문을 끝없이 붙이는 것이 아니다. `500 USDT는 언제든 써야 함` 같은 **사용자 확인 조건**, 선호하는 설명 방식, 거부한 상품, 승인된 루틴을 버전과 출처·수정 시각을 붙여 보관한다. 추론한 성향은 `확인 전`으로 남겨 사용자에게 정정할 수 있게 한다. 상품 금리·시장 현금·약관은 직원의 기억에 복사하지 않고 시점이 있는 FactStore에서 다시 읽는다. 계획·근거 묶음·사용자 정정·승인·체결 결과는 각기 별도 객체다.

금융 의사결정 코어(FDC)는 후보 계획을 만들고, 배분 오라클은 예산·출금·위험·시점·원문 연결을 검사한다. 직원 이름은 이 역할들의 사용자 경험 계층이다. ALPHA의 자신감이나 직원들끼리의 합의가 오라클의 증명이나 사용자 승인을 대체하지 않는다. 자동 검증은 [검토 운영 계약](../../research/REVIEW_ROUTING_20260924.md)에 따라 증명 범위를 명시하고, 소유자에게 개별 데이터 라벨 확인을 요구하지 않는다.

## 승인과 완료의 의미

승인 요청에는 계획 버전, 자산·수량·네트워크·대상 계약, 예상 총비용과 상한, 남는 잔액, 출금 조건, 견적 만료 시점, 원문 근거를 보여준다. 사용자의 명시적 승인 후에도 현재 자료·잔고·비용·허용 계약을 다시 검사하고 별도 지갑 서명이 필요하다. 실제 체결 확인 전에는 `구매 완료`라고 쓰지 않는다. 부분 성공·실패·미확정도 구별한다. 현재 제품의 `/api/approve`는 차단돼 있으므로 이 승인 카드는 향후 구현 계약이다.

## 구축 순서와 검증 기준

1. **정체성과 책임:** ALPHA·VAULT·WATCH 명단, 진짜 작업 상태, 역할별 읽기 권한. 개인 자산 연동이 없으면 빈 상태로 시작한다.
2. **지속성:** 사용자가 확인한 조건과 정정 이력, 계획 버전, 원천 갱신 이벤트, 루틴 실행 기록을 저장한다. 재방문 때 같은 ALPHA가 확인된 사실만 이어받는지 검사한다.
3. **결정 경험:** ALPHA 대화에서 VAULT·WATCH 작업이 자동 연결되고, FDC와 오라클의 판정으로 오른쪽 계획 카드가 갱신된다. 조건 변경 시 과거 카드가 무효가 되는지 검사한다.
4. **실행 연결:** 비용·출금 약관·권한·지갑 경로가 검증된 범위만 승인 카드를 연다. 승인·서명·체결 영수증을 분리해 확인한다.

핵심 지표는 직원 수가 아니라 **조건을 다시 설명한 횟수**, 유의미한 변화당 알림 수, 근거 없는 계획 노출률, 오래된 계획의 승인 차단률, 예외에서 사용자가 실제로 답해야 하는 질문 수, 승인 대비 확인된 체결 비율이다. 이 단계에서는 소비자 서비스 및 투자 자문 자격이나 실제 운용 성과를 주장하지 않는다.
